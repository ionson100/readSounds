# readSounds

Озвучивание текстовых файлов через локальный XTTS v2 (Coqui TTS) в Docker.
Avalonia 12 + .NET 9, Windows-клиент, который обращается к XTTS-серверу по HTTP.

Серверная часть — [XTTS v2](https://huggingface.co/coqui/XTTS-v2) из репозитория
[coqui-ai/TTS](https://github.com/coqui-ai/TTS), собрана и проверена на
**NVIDIA GeForce RTX 5080** с CUDA 12.8. Развёртывание описано в разделе
«Серверная часть», там же лежат `Dockerfile` и `docker-compose.yml`.

## Как это работает

Вы выбираете текстовый файл. Приложение режет его на части по точкам в конце
предложения, отправляет части на сервер по одной и склеивает полученные WAV
в один файл. Синтез можно остановить в любой момент, закрыть приложение и
позже продолжить ровно с того места.

## Требования

- .NET 9 SDK — только чтобы собрать программу
- Windows или Linux, если нужна готовая сборка: EXE и .deb самодостаточные,
  установленный .NET на них не требуется
- XTTS v2, поднятый в Docker: `tts-server` на порту 5002

Серверная часть разворачивается отдельно, см. раздел «Серверная часть».

## Запуск

```powershell
cd readSounds
dotnet run
```

В приложении: вкладка «Сервер и папки» → проверьте адрес (по умолчанию
`http://localhost:5002`, для удалённой машины укажите её IP) → «Сохранить и проверить».

Если XTTS живёт на другой машине в вашей сети, пробрасывайте порт наружу
в `docker-compose.yml` и указывайте IP этой машины в адресе.

## Сборка дистрибутивов

Скрипт `build.ps1` собирает два самодостаточных дистрибутива: EXE для Windows
и пакет `.deb` для Linux. **В обоих .NET находится внутри**, на машине
пользователя установленный рантайм не нужен.

Сборка кроссплатформенная: Linux-версия публикуется прямо из Windows, без
Docker и без установленного Linux.

### Ключи

| Ключ | Значение |
| --- | --- |
| `-Target` | `all` (по умолчанию), `windows` или `linux` |
| `-Version` | версия сборки; попадает в имя `.deb` и в свойства файлов |
| `-Configuration` | `Release` (по умолчанию) или `Debug` |
| `-OutputDirectory` | куда складывать результат, по умолчанию `./artifacts` |
| `-WindowsSingleFile` | упаковать Windows-сборку в один `.exe`; по умолчанию включено |

### Windows

```powershell
.\build.ps1 -Target windows
```

Результат — `artifacts\win-x64\readSounds.exe` (около 132 МБ). Это один файл:
рантайм .NET, нативные библиотеки Avalonia и значок внутри. Скопируйте его
куда угодно и запустите, установка не требуется.

Чтобы получить обычную папку вместо одного файла:

```powershell
.\build.ps1 -Target windows -WindowsSingleFile:$false
```

### Linux

```powershell
.\build.ps1 -Target linux
```

Результат — `artifacts\readsounds_1.2.0_amd64.deb` (около 43 МБ, имя
содержит подставленную версию). Установка на машине с Debian, Ubuntu или Mint:

```bash
sudo apt install ./readsounds_1.2.0_amd64.deb
readSounds
```

Пакет кладёт приложение в `/opt/readSounds`, создаёт симлинк `/usr/bin/readSounds`,
значок и запись в меню приложений. Пакет зависит от обычных библиотек X11
(`libx11-6`, `libice6`, `libsm6`, `libfontconfig1`, `libgl1`).

Удаление — `sudo apt remove readsounds`, вместе с приложением и значком.

### Обе платформы сразу

```powershell
.\build.ps1 -Version 1.2.0
```

### Что нужно скрипту

Только .NET 9 SDK и PowerShell. Скрипт рассчитан на Windows PowerShell 5.1
(который входит в состав Windows) и на PowerShell 7.

`dpkg-deb` не нужен: если его нет в системе, пакет склеивается вручную из
`debian-binary`, `control.tar.gz` и `data.tar.gz` в контейнере формата `ar`.
Если `dpkg-deb` есть (например, при запуске скрипта на Linux), упаковка пойдёт
через него.

### Особенности Linux-сборки

- **Прослушивание в приложении недоступно.** Оно идёт через waveOut из
  `NAudio.WinMM`, а это Windows. В Linux-сборке кнопки прослушивания скрыты,
  готовый WAV предлагается открыть системным плеером. Синтез, разбивка,
  склейка и продолжение работы доступны полностью.
- **Пути настраиваются иначе.** Настройки лежат в
  `$XDG_CONFIG_HOME/readSounds/settings.json` (обычно `~/.config`), папка
  проектов — в `XDG_DOCUMENTS_DIR`, иначе в домашней папке.
- **Открытие папки** идёт через `xdg-open` вместо `explorer.exe`.

### Значок

Значок один на обе платформы — `sound.png` в корне проекта. Он нигде не
дублируется вручную, обе сборки берут один и тот же файл.

- **Windows.** Перед публикацией скрипт собирает из него `Assets\sound.ico`
  семи размеров (16, 24, 32, 48, 64, 128, 256) и подключает через
  `ApplicationIcon` в `csproj`. Файл `.ico` производный, в репозиторий его
  класть не нужно: он пересобирается сам, если `sound.png` изменился. Windows
  показывает его в проводнике, на панели задач и в списке программ.
- **Linux.** `sound.png` копируется в пакет без изменений, в
  `usr/share/icons/hicolor/256x256/apps/readsounds.png`. Размер каталога
  читается из самого файла, а не задаётся: замените картинку на другую —
  путь останется верным. Рабочий стол и меню приложений найдут значок по
  имени `readsounds` из `.desktop`.

Если заменить `sound.png`, достаточно запустить `.\build.ps1` заново.

### Проверено

- EXE: 132.3 МБ, один файл, запускается и открывает окно приложения. Значок
  извлекается из готового EXE средствами Windows и совпадает с `sound.png`.
- .deb: 42.7 МБ, структура разобрана и проверена — 47 проверок. Контейнер `ar`
  с тремя членами, `debian-binary` = `2.0`, поля `control` заполнены, без CRLF
  и заканчиваются переводом строки, `postinst` и `prerm` с правами `0755`,
  приложение в `/opt/readSounds` с `libcoreclr.so`, `libhostfxr.so` и
  `libhostpolicy.so` внутри (то есть рантайм действительно приложен), значок
  совпадает с `sound.png` побайтово и читается как корректный PNG 256×256.

В `artifacts` остаются служебные папки `deb-staging` и `deb-work`: в первой
видно, что именно попадёт в пакет, во второй — распакованные `control.tar.gz`
и `data.tar.gz`. Их можно удалять, на результат они не влияют.

Саму установку через `dpkg -i` проверить не удалось: на машине сборки нет
ни `dpkg-deb`, ни Linux-системы. Проверена структура пакета и то, что
`tar` читает обе части архива.

## Серверная часть

Синтез выполняет XTTS v2, поднятый в Docker на машине с GPU. Собрано и
проверено на **NVIDIA GeForce RTX 5080**.

Ссылки:

- Репозиторий сервера: <https://github.com/coqui-ai/TTS>
- Модель XTTS v2: <https://huggingface.co/coqui/XTTS-v2>
- Образ CUDA: <https://hub.docker.com/r/nvidia/cuda>

### Требования

- NVIDIA GPU с драйвером и Docker с поддержкой GPU (на Windows —
  [WSL2](https://learn.microsoft.com/ru-ru/windows/wsl/install) либо
  [Docker Desktop с WSL-бэкендом](https://docs.docker.com/desktop/features/wsl/))
- CUDA 12.8 в образе: RTX 5080 относится к архитектуре Blackwell (`sm_120`),
  которую не поддерживают более ранние сборки PyTorch. Поэтому в `Dockerfile`
  зафиксированы базовый образ `12.8.1` и `--torch-backend=cu128`
- ~10 ГБ свободного места под образ и веса модели

### Установка

Положите рядом `Dockerfile` и `docker-compose.yml` (тексты ниже), затем
соберите и запустите:

```bash
docker compose build
docker compose up -d
```

Модель весит около 2 ГБ и при первом запуске скачивается сама: согласие с
условиями даёт переменная `COQUI_TOS_AGREED: "1"` в `docker-compose.yml`, без
неё загрузка не начинается. Скачанное попадает в том `tts_models`, поэтому
следующие запуски модель заново не качают. Дождитесь конца загрузки:
`healthcheck` в `compose` даёт `start_period: 120s`, потому что первый запуск
заметно дольше.

Проверка:

```bash
curl http://localhost:5002
```

В ответе — HTML-страница со списками голосов и языков. В этом же запросе
приложение их и читает: JSON-эндпоинта для каталога у XTTS нет.

Остановить: `docker compose down`. Удалить вместе с весами модели:
`docker compose down -v`.

### Настройка

В `docker-compose.yml` задаются:

| Параметр | Назначение |
| --- | --- |
| `ports` | `"${PORT:-5002}:5002"` — порт снаружи, 5002 по умолчанию |
| `gpus: all` | отдать контейнеру все видеокарты |
| `COQUI_TOS_AGREED` | `"1"` — согласие с лицензией, без него модель не скачается |
| `tts_models` | том с весами: повторный запуск не качает заново |
| `./voice_samples` | образцы голосов, `speaker_wav` читает отсюда |
| `./output` | куда сервер кладёт файлы при работе через API |
| `restart: unless-stopped` | поднимать сервер после перезагрузки |

Порт 5002 должен быть свободен. Если он занят, поменяйте левую часть
`${PORT:-5002}` и укажите тот же порт в адресе приложения.

При сборке Dockerfile печатает версии PyTorch, CUDA и имя GPU. Если там
`GPU: NONE`, контейнер собрался без видеокарты — синтез пойдёт на CPU и будет
значительно медленнее.

## Структура проекта

Каждый файл — отдельный проект, у проекта своя самодостаточная папка:

```
readSounds Projects/
  Моя книга/
    project.json      язык, голос, порог длины части, прогресс
    book.txt          копия исходного текста
    audio/result.wav  результат, растёт по мере синтеза
```

Копия исходника лежит в проекте, поэтому проект переживает перемещение папки
и правку оригинала. Настройки лежат в `project.json` рядом с текстом.

## Разбивка на части

Порог «символов в части» — **мягкий**. Главное правило: не разрывать предложение.
Лучше отдать часть длиннее порога, чем озвучить обрывок фразы — интонация на
стыке слышна, и смысл теряется.

Для части, начинающейся в позиции `start`, граница выбирается так:

1. **первая точка на пороге или дальше, но не дальше `2 × порог`** — часть длиннее
   порога (например 245 при пороге 200);
2. если в этом окне точек нет — **последняя точка до порога**, часть короче
   порога (например 136);
3. точек нет вовсе — разрез по ближайшему пробелу у порога, иначе строго по порогу.

Верхняя граница окна (правило 1) существует потому, что без неё правило 1 всегда
перебивало бы правило 2: граница в конце текста есть по определению, и ждать
точку «сколько угодно» нельзя — одна фраза на пять тысяч символов стала бы одной
«частью». Коэффициент задан константой `MaxOvershootFactor` в `TextChunker`.

Границами считаются точка, `!`, `?`, `…` и перенос строки. Сокращения и инициалы
(«г. Москве», «И. Иванов», «т.д.», «стр. 45») и точка внутри числа («3.14»)
границами не считаются.

Часть, у которой разорвана фраза хотя бы с одного края, помечается в списке
значком ⚠ — по ней слышно, что интонация местами пойдёт не туда.

**Жёсткого предела у XTTS нет.** Сервер сам режет текст на предложения
(`split_sentences=True` в `Synthesizer.tts`), поэтому длинная часть не мешает:
она просто станет несколькими предложениями на стороне сервера.

## Продолжение после закрытия

Состояние сохраняется после каждой части: `project.json` хранит, сколько частей
готово и сколько байт PCM записано. При следующем запуске файл обрезается до
отметки последней целой части — недописанный хвост после аварийного закрытия
отбрасывается — и синтез продолжается с первой неозвученной части.

Если исходный текст или настройки (язык, голос, порог) изменились после начала
работы, приложение предупредит: продолжать нельзя, нужно «Начать заново».
Иначе в файле оказались бы куски, озвученные разными голосами.

## Склейка аудио

Куски склеиваются побайтовой конкатенацией PCM без перекодирования: сервер
отдаёт WAV, программа разбирает RIFF-заголовок, проверяет совпадение формата
всех частей (24 кГц, mono, 16 бит) и дописывает сырые данные. Поэтому
`result.wav` — один обычный WAV-файл, который открывается любым плеером.

Перед склейкой каждый кусок проходит через `ChunkPreparer`:

- **Обрезка тишины по краям.** XTTS почти всегда отдаёт кусок с тишиной в
  начале и в конце. Склеенные как есть, два соседних куска дают на стыке
  тишину конца плюс тишину начала — слышимые паузы там, где их нет в тексте.
  Края срезаются, но с запасом 15 мс, чтобы не отрезать взрывной согласный.
- **Затухание 5 мс по краям.** Последний отсчёт куска и первый отсчёт
  следующего — независимые значения, и на стыке возникает скачок, который
  слышен как щелчок. Затухание сводит стык к нулю.

На реальных файлах обрезка убирала около 0.6 с лишней паузы на файл
(60.03 с → 59.45 с в проекте из 9 частей).

### Откуда берутся «лишние звуки»

Разбор файлов показал, что часть аномалий — не от склейки, а от самой модели.
Это важно понимать, чтобы не искать причину не там:

- **Всплески шума внутри куска.** В проверенных файлах нашлось 131 одиночный
  выброс на проекте из 9 частей — полноразмахные, но окружённые тихими
  отсчётами. Они лежат *внутри* кусков, а не на стыках, и после обрезки краёв
  остаются ровно те же 131. То есть это артефакт генерации XTTS, а не дефект
  склейки.
- **Темп речи.** В обоих проверенных проектах он был ниже нормы (11.0 и 8.8
  знака в секунду при норме чтения 12..17). Это следствие пауз внутри
  генерации, а не лишних слов.

Часть с ненормальным темпом помечается: после синтеза появляется список
номеров, и каждую такую часть можно переозвучить отдельно.

## Переозвучка одной части

Испорченный кусок можно переделать, не трогая остальные. В `project.json`
хранится `ChunkEnds` — смещение конца каждой готовой части в байтах. По кнопке
«Переозвучить» файл обрезается до границы предыдущей части, и синтез идёт
дальше обычным ходом, дописывая только недостающее.

Проекты, созданные до появления `ChunkEnds`, границ частей не помнят. Для них
программа прямо говорит об этом и предлагает «Синтезировать заново», вместо
того чтобы падать.

## О структуре кода

```
Models/       ProjectModel, ProjectOptions, ProjectProgress, AppSettings, TtsCatalog
Services/
  TextChunker.cs      разбивка текста на части
  TextFileReader.cs   чтение с определением кодировки (BOM → UTF-8 → CP1251 → Latin-1)
  WavReader.cs        разбор WAV
  Audio/              WavConcatWriter — наращиваемый WAV, склейка и обрезка хвоста
                      ChunkPreparer — обрезка тишины по краям и затухание на стыках
  TtsClient.cs        HTTP к XTTS: GET /api/tts, чтение списка голосов с /
  HtmlCatalogParser.cs  разбор HTML главной страницы сервера
  TextNormalizer.cs   типографские символы -> понятные модели, перед отправкой
  SynthesisService.cs цикл синтеза, сохранение состояния, продолжение
```

## Особенности XTTS, о которых стоит знать

**Список голосов и языков берётся из HTML.** У `tts-server` нет JSON-эндпоинта
для списков — он подставляет их в шаблон страницы из конфига модели. Приложение
парсит `<select id="speaker_id">` и `<select id="language_id">`. Если сервер
недоступен, используется встроенный набор XTTS v2 (58 голосов, 17 языков).

**Пустые `language_id` и `speaker_id` дают 500.** Сервер делает так:
`if language_idx == "": language_idx = None`, и XTTS отвечает
`500 {"error": "TTS synthesis failed: Model is multi-lingual but no `language` is provided."}`.
Поэтому клиент проверяет оба значения до запроса и пустые не отправляет.

Язык и голос **не подставляются по умолчанию**: если язык не выбран, синтез
заблокирован и под настройками написано, что выбрать. Иначе русский текст тихо
озвучился бы голосом `en` — брак, о котором вы бы и не узнали. В окне проекта
видно, что реально уходит на сервер:
`language_id=ru · speaker_id=Claribel Dervla`.

**Ошибки приходят в JSON.** Актуальный `coqui-tts` отдаёт `{"error": "..."}`,
и текст внутри ключа полезнее обёртки — клиент достаёт именно его.
Пустой `text` сервер отвергает кодом 400.

**Обновление списка голосов не обнуляет выбор.** Очистка списка сбрасывает
`SelectedItem` в null, а двусторонняя привязка записала бы null в `project.json` —
после этого XTTS получал бы пустой `language_id` и отвечал 500. Выбор
восстанавливается вручную, на время перезаполнения сохранение отключено.

**`speaker_wav` сервер поддерживает.** В `server.py` форка idiap параметр
передаётся в модель: `api.tts(text, speaker=..., language=..., style_wav=...,
speaker_wav=...)`. Приложение пока его не использует. Если понадобится свой
голос, заготовка рядом: `TtsClient.BuildTtsUri`, путь указывается внутри
контейнера (у вас это `/voice_samples/...`).

**Запросы идут строго последовательно.** Внутри `tts-server` стоит глобальный
`Lock`, поэтому параллельные запросы всё равно выстроились бы в очередь.
Клиент сериализует их явно.

**Почему WAV, а не mp3.** Взвешено, решение — оставить WAV. Проверено по исходникам:

- `/api/tts`, который использует приложение, отдаёт только WAV — параметра
  формата там нет;
- `POST /v1/audio/speech` (OpenAI-совместимый, он есть в `coqui-tts 0.27.5`)
  заявляет `response_format: mp3`, но mp3 там фактически не кодируется: сервер
  вызывает `torchaudio.save(io.BytesIO(), ..., format="mp3")`, а в torchaudio ≥ 2.9
  (у вас 2.11) параметр `format` игнорируется — формат определяется расширением
  файла, а у `BytesIO` расширения нет;
- язык на `/v1/audio/speech` берётся из аргумента сервера `--language_idx`
  (дефолт `"en"`), а не из запроса, то есть стал бы фиксированным для всех проектов.

Кодировать у себя тоже нечем: в NAudio только MP3-декодер, готового энкодера
в NuGet нет, MP3-энкодер Windows убран — остаётся ffmpeg, а его на машине нет.
Если вопрос вернётся: `result.wav` остаётся рабочим файлом, mp3 делается из
него отдельной командой, так что логику склейки и продолжения трогать не придётся.

**Системный прокси отключён намеренно.** XTTS живёт в локальной сети или на
localhost, а VPN-клиенты (Hiddify и подобные) отправляют такие запросы наружу,
где их обрывают. В `TtsClient` выставлен `UseProxy = false` — иначе при
включённом прокси соединение падало бы с разрывом.

**503 — это не поломка.** XTTS отдаёт 503, пока модель прогревается на GPU.
Приложение покажет текст ошибки и подсказку об этом; после прогрева нажмите
«Продолжить».

## Подготовка текста перед отправкой

**Знаки ударения в XTTS не работают.** Разбирал конвейер модели: после чистки
текст уходит прямо в BPE-токенизатор, и шага, который обработал бы знак ударения,
там нет. Модель обучена на тексте без ударений и ударение предсказывает сама из
букв, поэтому расстановка в исходнике не повлияет на озвучку — знак лишь
превратится в `[UNK]`. Русское фонематизирование в XTTS не подключено, обходного
пути нет.

Что действительно работает — контекст. Изолированные слова-омонимы читаются
неверно, а внутри связного предложения модель ошибается реже, поэтому разбивка на
целые фразы (см. выше) сама по себе поднимает качество ударений. Дальше —
лексическая правка («слезы́» → «слёзы») или смена модели: XTTS многоязычный, и
надёжного русского ударения в нём не предусмотрено.

**Типографские символы чистятся автоматически.** Чистка на сервере вырезает
только ASCII-кавычки `"`. Типографленные кавычки она не трогает, а в словаре модели
их нет — каждая уходит в `[UNK]` и засоряет озвучку. Перед отправкой
`TextNormalizer` заменяет:

- английские и «ёлочки» → `"`, чтобы сервер вырезал их совсем;
- одинарные типографские → `'`;
- тире (en, em, горизонтальное, figure) и минус → `-`;
- неразрывный, узкий, тонкий, волосяной и цифровой пробелы → обычный;
- мягкий перенос, zero-width space, ZWNJ, ZWJ, word joiner, BOM → удаляются.

Исходный файл в проекте **не меняется** — правится только то, что уходит на
сервер. Разбивка на части и состояние продолжения считаются по исходнику, поэтому
ничего не расходится. Сколько замен будет сделано, видно под списком разбивки и
в прогрессе во время синтеза.

Сервер и сам приводит числа («50» → «пятьдесят»), проценты, валюты и сокращения
(`г-н` → `господин») — вручную это делать не нужно.

## Показ ошибок

Исключение больше не убивает приложение молча. Три уровня перехвата:

- `MainWindow` ловит ошибки открытия проекта и создания нового, показывая
  окно с текстом проблемы;
- `Dispatcher.UIThread.UnhandledException` — всё, что вылетело в UI-потоке
  вне этих обработчиков;
- `AppDomain.UnhandledException` и WinAPI-диалог — когда окно Avalonia показать
  уже нечем (например, ошибка при инициализации).

Подавленные ошибки пишутся в stderr, поэтому их видно при запуске из консоли.
